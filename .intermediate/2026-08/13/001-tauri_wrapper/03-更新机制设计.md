# 03 · 更新机制设计

> 更新对象：**dsh 运行时**（`@deepseek-ai/dsh` npm 包及其依赖闭包）。
> 桌面壳自身的更新走 tauri-plugin-updater，属 M5 可选范畴，与本章机制正交。

## 1. 总体流程

```
[触发] 启动时 / 定时(12h) / 菜单·托盘"检查更新"
   │
   ▼
[检测] GET https://<registry>/@deepseek-ai%2Fdsh   (reqwest, 超时 10s)
   │     取 dist-tags[channel]（latest|next，settings 可配）
   │     与 current 版本做 semver 比较
   ▼
[提示] 有新版 → 事件 update-available（托盘气泡/设置页红点）
   │     autoUpdate=false → 等待用户点"更新"
   │     autoUpdate=true  → 直接进入安装（静默或最小打扰，见 §5）
   ▼
[安装] 蓝绿安装：npm install 到 versions/<new>/（不触碰 current 指向的版本）
   │     全程事件 update-progress：resolving → fetching → installing → verifying
   ▼
[验证] node versions/<new>/…/lib/bin.js --version 必须等于 <new>
   │     （失败 → 清理新目录，报告失败，现状不受影响）
   ▼
[切换] 写 current.tmp（内容=新版本目录绝对路径）→ rename 覆盖 current   ← 原子
   ▼
[重启] SIGTERM 旧子进程 → 以新版本重走启动序列 → WebView 重载
   │     同时把旧版本登记为 rollback 候选（保留最近 2 个历史版本）
   ▼
[完成] settings.lastCheck 更新；更新记录写 changelog.json
```

## 2. 版本检测（RegistryClient）

- **首选**：直接 GET registry HTTP API
  - `https://registry.npmjs.org/@deepseek-ai%2Fdsh`（URL 编码的 scoped 包名）
  - 取 `dist-tags.latest` / `.next`、`time` 中对应版本的发布时间、`versions[ver].dist.{tarball,shasum,integrity}`。
  - 优点：不经过 npm CLI、不受 `~/.npm` 缓存损坏影响（本机已踩坑，见 01§6）、无额外进程。
- **后备**（registry 不可达时）：`npm view @deepseek-ai/dsh version --cache <appdata>/npm-cache --json`——仅当用户明确配置了镜像且 API 结构不同时兜底。
- **semver 比较**：Rust `semver` crate。`latest` 与 `next` 当前同为 `0.1.0-rc.6`；rc 迭代期建议默认通道 `latest`，把 `next` 作为"尝鲜"选项。
- **镜像支持**：`settings.registry` 默认为官方源，用户可改 `https://registry.npmmirror.com`（安装与检测统一走该镜像，`npm install --registry` 同步生效）。
- **防抖**：`lastCheck` 时间戳 + 最小间隔（默认 30 min），避免频繁轮询。

## 3. 蓝绿安装（Installer）

```
versions/
├─ 0.1.0-rc.3        (历史，可回滚)
├─ 0.1.0-rc.6        (current → 运行中，读多不写)
└─ 0.1.0-rc.7        (安装中 → 验证 → 切换后成为新 current)
```

- **安装命令**（跨平台，Windows 下经 `cmd /C` 或 powershell 适配引号）：
  ```
  npm install @deepseek-ai/dsh@<精确版本> --prefix <appdata>/runtime/versions/<ver> \
       --cache <appdata>/npm-cache --no-audit --no-fund --loglevel error --registry <settings.registry>
  ```
  关键点：`--cache` 独立缓存（硬约束）；`@<精确版本>` 防止 semver 漂移；`--prefix` 落到全新目录，全程不写 `current` 指向的目录。
- **验证**（切换前，缺一不可）：
  1. `node <ver>/node_modules/@deepseek-ai/dsh/lib/bin.js --version` 输出 == 目标版本；
  2. 可选冒烟：`--dump-default-config` 能正常输出（不真正起服务，避免抢端口）。
- **切换**：`write(current.tmp) → fsync → rename(current)` 原子替换；随后才允许停止旧子进程。
- **失败语义**：安装/验证任何一步失败 → 删除半成品目录 → 状态回 "可用"；**运行中的 dsh 零影响**（这正是蓝绿的意义）。
- **回滚**：菜单/设置页"回退到上一版本" = 指针指回历史目录 + 重启；历史目录保留最近 2 个 + 每季度清理更旧的（settings 可配）。

## 4. 一致性风险与对策

| 风险 | 对策 |
|------|------|
| 更新与运行并发写同一目录 | 蓝绿隔离：current 指向的目录永不被安装流程写 |
| 切换瞬间崩溃 | 指针原子 rename；启动序列发现指针文件损坏时自动回退到 versions 中最新完整版本 |
| 新版启动失败（握手超时） | 自动回滚：若新版本握手失败且旧版本目录还在，指针回退 + 重启旧版 + 错误页提示"已回滚" |
| 网络中断半成品 | 安装目录以版本号命名，失败即删；`current` 永不指向半成品 |
| 磁盘空间不足 | 安装前检查 `df`（≥ 500MB 余量，实测单版本安装 334MB）+ 安装后清理策略 |
| npm 并发互斥 | `.locks/install.lock` 文件锁（`fs2` crate），bootstrap 与更新互斥 |

## 5. 自动/手动策略（产品行为）

| 场景 | 行为 |
|------|------|
| **自动更新（默认开）** | 启动 + 每 12h 检测；发现新版后若用户正在使用 → 静默后台安装，**等 dsh 空闲/用户退出时重启生效**（v1 简化为：安装完成后托盘提示"新版本已就绪，点击重启生效"） |
| **手动更新** | 菜单/托盘/设置页"检查更新"→ 展示当前/最新/发布时间 → 用户点"更新"→ 进度条 → 重启生效 |
| **关闭自动更新** | 仅手动触发；仍允许设置页显示"有新版本"徽标 |
| **更新失败** | 托盘错误提示 + 设置页展示失败原因与日志入口；不影响 dsh 运行 |
| **回滚** | 设置页"运行历史"列出可用历史版本，一键回退 |

v1 不做热切换（dsh 会话状态在进程内，重启必然丢失当前会话上下文），在重启前弹确认："重启会中断当前会话，是否继续？"——这一限制在 UI 文案中明示。

## 6. 壳自更新（M5 可选，正交）

- 桌面壳本身（Rust 产物）用官方 `tauri-plugin-updater` + 静态 JSON 端点（GitHub Releases）：`latest.json` 含 version/notes/signature。
- 与 dsh 运行时更新完全独立：壳更新改的是 .app/.exe 二进制，dsh 更新改的是应用数据目录里的 JS 运行时。
- macOS 分发需签名（`APPLE_CERTIFICATE`）+ 公证；签名密钥用于 updater 签名校验。
